# 中文

## kube-accelerator-sim v0.7.1

v0.7.1 把「厂商加速卡特性写入 Node 标签」从 NVIDIA 扩展到 AMD、Intel、华为
昇腾与阿里云 PPU，全部取值逐字取自第一方文档，不从模型 ID 或资源名反推。

本次调研确认：**除 NVIDIA 外的厂商同样需要把加速卡特性写成 Node 标签**，但实现
分两条路线——NVIDIA、AMD、Intel 经由 Node Feature Discovery（NFD）注入，昇腾、
寒武纪、阿里 PPU、海光、沐曦、摩尔线程等由设备插件直接 patch Node。因此 NFD
不是这些标签的前提，只是一种实现路线。Kasim 投射的是最终标签，不建模由谁写入，
本版也不新增 NFD 或 `feature.node.kubernetes.io/*` 命名空间的投射能力。

### 主要变化

- `amd` profile 新增 `labeller` 证据（grade A，锚定 `2af2fdb`，即
  `cmd/k8s-node-labeller/README.md`），并在 `device-plugin` 契约上声明 6 个
  identity signal：`amd.com/gpu.cu-count`、`amd.com/gpu.device-id`、
  `amd.com/gpu.family`、`amd.com/gpu.product-name`、`amd.com/gpu.simd-count`、
  `amd.com/gpu.vram`。`amd-mi300x` 取得 4 个取证取值（`cu-count=304`、
  `device-id=74a1`、`product-name=AMD_Instinct_MI300X_OAM`、`simd-count=1216`）。
  `family` 与 `vram` 保留已声明键但无取值：文档给出的 family 缩写表未覆盖 CDNA
  系列，vram 只公布了 legacy `16G` 形式示例。
- `intel-gpu` profile 新增 `labels` 证据（grade A，锚定 `6460392`，即
  `cmd/gpu_plugin/labels.md`），声明 `gpu.intel.com/family` 与
  `gpu.intel.com/product` 两个 identity signal，并派生
  `gpu.intel.com/device.count`（`pool-total-capacity`）。`intel-max-1550`
  （`Max_Series` / `Max_1550`）与 `intel-flex-170`（`Flex_Series` /
  `Flex_170`）取得取证取值。文档列出四个已覆盖平台，但只为这两个型号公布了
  样值，Flex 140 与 Max 1100 保留空值。
- `huawei-ascend` profile 在 `device-plugin` 契约上新增 `accelerator`
  identity signal，取值 `huawei-Ascend310` / `huawei-Ascend310P` /
  `huawei-Ascend910`，锚定 MindCluster v26.1.0。官方「集群调度对 Node label
  使用说明」表逐条标注该键的写入组件为 Ascend Device Plugin，与设备插件直写
  路线一致。`huawei-atlas-a2` 不重复填值（官方表为其列出的 `huawei-Ascend910`
  与其芯片家族已携带的值相同），`huawei-atlas-a3` 仍不输出 vendor 标签。
- `alibaba-ppu` profile 补齐节点级与型号级分层：`device-plugin` 契约声明
  `aliyun.accelerator/ppu_name` 与 `aliyun.accelerator/ppu_mem` 两个身份键，
  并派生 `aliyun.accelerator/xpu_type`（`static`，值 `ppu`）与
  `aliyun.accelerator/ppu_count`（`pool-total-capacity`）。`alibaba-ppu-zw810e`
  取得 `PPU-ZW810E` 与 `98304MiB`；`alibaba-ppu-m890p` 无样值，不填。
- 新增 `internal/projection/vendor_discovery_labels_test.go`：逐厂商断言
  `discoveryLabels: true` 时的取证取值、省略开关时全部取值消失，以及「已声明但
  无取证取值」的键仍保留为空值的行为。
- 未取证的键保持原样并在文档中记录：`cambricon`（`Model`）、`hygon`
  （`hygon.com/dcu*` 4 个键）、`metax`（`metax-tech.com/gpu.topology.*` 2 个键）、
  `moore-threads`（`mthreads.com/gpu`）没有第一方节点标签证据，目录不为其编造
  取值。这些键仍投射为空值，从而保留冲突占位且不会错误满足正向 `nodeSelector`。
- Profile Catalog revision 升级为 `2026-09-16.2`，摘要更新为
  `sha256:9d62e9fb8f50eca1030eb91b29a6dc3d141d56e79c205d5e9fc81e3288833ae2`；
  Telemetry Catalog revision 与摘要不变
  （`2026-09-16.1` / `sha256:80157a7e1720cb5e064a6dbd5e444845d540e8cf43854156a838dec43737786e`）。
  Chart 注解、`release/inputs.json`、示例与 golden 基线同步。
- 中英文运维文档 `node-discovery-labels`（新增「各厂商如何发布这些标签」路线表、
  AMD / Intel / 阿里 PPU 章节、华为昇腾补充 `accelerator`、「无取证取值的键」
  章节、边界中明确不投射 NFD 自有命名空间）、`profile-evidence`（新增两条
  evidence anchor 与「节点发现标签覆盖范围」表）、`scenario-examples` 与
  `examples/README.md` 同步更新。
- Bump product and chart version to 0.7.1。

### 升级说明

该版本不更改 Scenario CRD、调度资源或 Kubernetes 支持范围；仍支持 Kubernetes
1.30–1.36。

**目录 revision 变化意味着既有场景实例不可原地升级。** 实例钉住提交时的 profile
revision 与 digest，升级 runtime 前必须先删除所有既有场景实例，在空集群上完成
`helm upgrade`，再用新 CLI 重新提交。

`discoveryLabels` 仍是按 Node Group 的显式开关。既有未开启该开关的场景，规范
场景字节与摘要完全不变。

# English

## kube-accelerator-sim v0.7.1

v0.7.1 extends accelerator Node label projection from NVIDIA to AMD, Intel,
Huawei Ascend, and Alibaba Cloud PPU, with every value taken verbatim from
first-party documentation and nothing reverse-engineered from a model ID or a
resource name.

The research behind this release confirms that **vendors other than NVIDIA also
need card properties published as Node labels**, but they split across two
routes: NVIDIA, AMD, and Intel inject them through Node Feature Discovery
(NFD), while Huawei Ascend, Cambricon, Alibaba Cloud PPU, Hygon, MetaX, Moore
Threads, and others patch Nodes directly from the device plugin. NFD is
therefore not a prerequisite for the labels — it is one implementation route.
Kasim projects the resulting labels rather than modeling the writer, and this
release adds no NFD capability and no projection of the
`feature.node.kubernetes.io/*` namespace that NFD itself owns.

### Highlights

- The `amd` profile gains a `labeller` evidence record (grade A, pinned to
  `2af2fdb`, `cmd/k8s-node-labeller/README.md`) and declares six identity
  signals on its `device-plugin` contract: `amd.com/gpu.cu-count`,
  `amd.com/gpu.device-id`, `amd.com/gpu.family`, `amd.com/gpu.product-name`,
  `amd.com/gpu.simd-count`, and `amd.com/gpu.vram`. `amd-mi300x` carries four
  evidenced values (`cu-count=304`, `device-id=74a1`,
  `product-name=AMD_Instinct_MI300X_OAM`, `simd-count=1216`). `family` and
  `vram` keep their declared keys with no value: the documented family acronym
  table does not cover CDNA parts, and `vram` publishes only a legacy `16G`
  sample.
- The `intel-gpu` profile gains a `labels` evidence record (grade A, pinned to
  `6460392`, `cmd/gpu_plugin/labels.md`), declares `gpu.intel.com/family` and
  `gpu.intel.com/product`, and derives `gpu.intel.com/device.count` from
  `pool-total-capacity`. `intel-max-1550` (`Max_Series` / `Max_1550`) and
  `intel-flex-170` (`Flex_Series` / `Flex_170`) carry evidenced values. Intel
  documents four covered platforms but publishes sample values for these two
  only, so Flex 140 and Max 1100 keep empty values.
- The `huawei-ascend` profile declares a new `accelerator` identity signal on
  its `device-plugin` contract, with values `huawei-Ascend310`,
  `huawei-Ascend310P`, and `huawei-Ascend910`, anchored to MindCluster v26.1.0.
  The official Node label usage table names Ascend Device Plugin as the writing
  component for that key, matching the device-plugin route.
  `huawei-atlas-a2` does not duplicate a value — the official table lists
  `huawei-Ascend910` for it, which its chip family already carries — and
  `huawei-atlas-a3` still emits no vendor label.
- The `alibaba-ppu` profile now separates node-level from model-level data: the
  `device-plugin` contract declares `aliyun.accelerator/ppu_name` and
  `aliyun.accelerator/ppu_mem` as identity signals and derives
  `aliyun.accelerator/xpu_type` (`static`, value `ppu`) and
  `aliyun.accelerator/ppu_count` (`pool-total-capacity`).
  `alibaba-ppu-zw810e` carries `PPU-ZW810E` and `98304MiB`; `alibaba-ppu-m890p`
  publishes no sample values and stays empty.
- New `internal/projection/vendor_discovery_labels_test.go` asserts, per
  vendor, the evidenced values under `discoveryLabels: true`, the absence of
  every value when the switch is omitted, and the retained-but-empty behavior
  of declared keys without evidenced values.
- Keys without evidence remain unchanged and are documented as such:
  `cambricon` (`Model`), `hygon` (four `hygon.com/dcu*` keys), `metax` (two
  `metax-tech.com/gpu.topology.*` keys), and `moore-threads`
  (`mthreads.com/gpu`) have no first-party node label evidence, and the catalog
  never fabricates values for them. They still project as empty values, which
  keeps their collision reservation and never satisfies a positive
  `nodeSelector` match.
- The Profile Catalog revision advances to `2026-09-16.2` with digest
  `sha256:9d62e9fb8f50eca1030eb91b29a6dc3d141d56e79c205d5e9fc81e3288833ae2`;
  the Telemetry Catalog revision and digest are unchanged
  (`2026-09-16.1` /
  `sha256:80157a7e1720cb5e064a6dbd5e444845d540e8cf43854156a838dec43737786e`).
  Chart annotations, `release/inputs.json`, the examples, and the golden
  baselines are synchronized.
- English and Chinese operator documentation is updated: `node-discovery-labels`
  gains the vendor route table, AMD / Intel / Alibaba Cloud PPU sections, the
  Ascend `accelerator` key, a "keys without an evidenced value" section, and a
  boundary stating that Kasim does not project the NFD-owned namespace;
  `profile-evidence` gains two evidence anchors and a node discovery label
  coverage table; `scenario-examples` and `examples/README.md` follow.
- Bump product and chart version to 0.7.1.

### Upgrade notes

This release does not change the Scenario CRD, scheduling resources, or the
Kubernetes support range. Kubernetes 1.30–1.36 remains supported.

**A changed catalog revision means existing Scenario Instances cannot be
upgraded in place.** Instances pin the profile revision and digest they were
submitted with, so every existing instance must be deleted before upgrading the
runtime, the `helm upgrade` must run against an empty cluster, and the Scenarios
must then be resubmitted with the new CLI.

`discoveryLabels` remains an explicit per-Node-Group opt-in. For existing
Scenarios that leave it off, the canonical Scenario bytes and digests are
unchanged.

# 中文

## kube-accelerator-sim v0.5.2

v0.5.2 修复启用 ServiceMonitor 后，逐设备遥测指标无法通过
`on(namespace, pod)` 与抓取目标元数据关联的问题。ServiceMonitor 现在保留
Prometheus 注入的 `namespace` 和 `pod`，仅移除 `container`；原厂指标名、原厂
label、Synthetic Node 归属以及模拟数值生成逻辑均保持不变。

### 主要变化

- 可选 ServiceMonitor 的 metric relabeling 从删除 `namespace`、`pod`、
  `container` 调整为仅删除 `container`。
- 使用 `on(namespace, pod)` 的现有清单或应用元数据关联查询可以匹配集中式
  Kasim telemetry 抓取目标，不再因目标身份 label 缺失而得到空结果。
- 保留的 `namespace` 和 `pod` 只描述位于 `kasim-system` 的集中式 telemetry
  Pod。它们不表示 Synthetic Node，也不表示业务 Pod 拥有、预留或使用模拟设备。
- 设备归属继续以逐卡指标的 `node` 及 exporter 原生节点 label（例如 DCGM 的
  `Hostname`）为准。监控后端应把 Kasim telemetry 目标识别为基础设施组件。
- 增加 Helm Chart 回归测试，固定“保留 `namespace`/`pod`、仅删除
  `container`”的抓取契约；规范、ADR 与中英文运维文档同步更新。
- Telemetry 公共表面版本升级为 `v1alpha4`。Telemetry Catalog 内容、修订和摘要
  未变化。

### 升级说明

该修复只改变启用 `telemetry.serviceMonitor.enabled=true` 时 Prometheus 抓取后的
目标 label。Scenario CRD、调度资源、逐设备 UUID/索引、厂商指标格式、Kubernetes
集群生命周期和支持范围均不变；仍支持 Kubernetes 1.30–1.36。

若使用 Chart 自带 ServiceMonitor，升级后等待 Prometheus 下一次抓取即可。若使用
注解或外部抓取配置，应自行保留等价的 `namespace`、`pod` 目标身份，并只把它们
用于抓取目标关联，不能据此覆盖设备指标中的模拟节点身份。

### 发布产物

- GitHub Release：Linux amd64/arm64、macOS amd64/arm64、Windows amd64 原生
  `kasim` CLI 归档，以及校验和、SBOM、发布证据和 Sigstore 签名。
- Docker：`ghcr.io/linkmaq/kube-accelerator-sim-controller:0.5.2`，同一最小
  运行时镜像包含 `/kasim-controller` 与 `/kasim-telemetry`。
- Helm OCI：`oci://ghcr.io/linkmaq/charts/kasim-runtime`，版本 `0.5.2`。

# English

## kube-accelerator-sim v0.5.2

v0.5.2 fixes per-device telemetry queries that could not join scrape-target
metadata with `on(namespace, pod)` when the ServiceMonitor was enabled. The
ServiceMonitor now retains Prometheus-injected `namespace` and `pod` labels
and removes only `container`. Native metric names and labels, Synthetic Node
ownership, and simulated value generation are unchanged.

### Highlights

- The optional ServiceMonitor metric relabeling now drops only `container`
  instead of dropping `namespace`, `pod`, and `container`.
- Existing inventory or application-metadata queries using
  `on(namespace, pod)` can match the centralized Kasim telemetry scrape target
  instead of returning an empty result because target identity was absent.
- The retained `namespace` and `pod` labels describe only the centralized
  telemetry Pod in `kasim-system`. They do not identify a Synthetic Node or
  assert that a workload Pod owns, reserves, or uses a simulated device.
- Device placement continues to use each series' `node` label and native
  exporter Node identity, such as DCGM `Hostname`. Monitoring backends should
  classify the Kasim telemetry target as infrastructure.
- A Helm Chart regression test pins the contract that preserves
  `namespace`/`pod` and drops only `container`; the specification, ADR, and
  English and Chinese operator documentation are synchronized.
- The telemetry public surface advances to `v1alpha4`. The Telemetry Catalog
  contents, revision, and digest are unchanged.

### Upgrade notes

This fix changes only Prometheus target labels after scraping when
`telemetry.serviceMonitor.enabled=true`. The Scenario CRD, scheduling
resources, per-device UUIDs and indices, vendor metric formats, Kubernetes
cluster lifecycle, and support range are unchanged. Kubernetes 1.30–1.36
remains supported.

When using the chart-managed ServiceMonitor, wait for the next Prometheus
scrape after upgrading. Annotation-based or externally managed scraping should
preserve equivalent `namespace` and `pod` target identity, use it only for
scrape-target joins, and never overwrite the simulated Node identity carried
by device series.

### Artifacts

- GitHub Release: native `kasim` CLI archives for Linux amd64/arm64, macOS
  amd64/arm64, and Windows amd64, plus checksums, SBOM, release evidence, and a
  Sigstore signature.
- Docker: `ghcr.io/linkmaq/kube-accelerator-sim-controller:0.5.2`; the same
  minimal runtime image contains `/kasim-controller` and `/kasim-telemetry`.
- Helm OCI: `oci://ghcr.io/linkmaq/charts/kasim-runtime`, version `0.5.2`.
